# 계산 계약과 검증 근거

## 입력과 결과

`Session`은 관측 시작/종료의 ISO offset timestamp와 **알려진 시계 오차**를 갖습니다. 오차의 부호는 `기록 시계 - 기준 시계`입니다. 예를 들어 실제 00:00:00을 장비가 00:00:02로 기록했다면 +2초를 빼서 보정합니다. 이 예제는 보정값이 주어졌다고 가정하며 NTP 동기화나 오차 추정기를 구현하지 않습니다. 시스템 시계는 변경하지 않습니다.

시간창은 양의 길이, 최대 1시간이고 입력은 최대 4,096세션입니다. 오차는 ±5분 안이어야 합니다. `Z` 또는 명시적인 `±HH:MM` offset 없는 timestamp는 거부합니다. ID는 최대 64자의 소문자 ASCII이며 중복을 거부합니다. null, 역전·동일 시작/종료, 범위 초과 입력은 고정 오류로 거부합니다. 보정한 UTC 종료 시점이 시작보다 늦어야 하며 시간창 밖 세션은 제외하고 걸친 세션은 잘라냅니다.

모든 구간은 반열린 `[시작, 종료)`입니다. `[0,10)`과 `[10,20)`의 최대 동시는 1입니다. 같은 시점의 start/end delta를 합친 뒤 다음 구간의 active 수를 관측합니다. 결과 `coveredNanos`는 겹친 시간을 한 번만 센 합집합의 길이이며 `peakConcurrentSessions`는 최대 동시 **관측 세션** 수입니다. 물리 센서 ID를 기준으로 중복 제거하는 계산은 아닙니다.

원본 timestamp는 `OffsetDateTime.toInstant()`로 실제 UTC timeline으로 옮긴 다음 알려진 오차를 뺍니다. 잘라낸 endpoint만 시간창 시작 기준 정수 nanosecond로 변환합니다. 최대 1시간 제한을 `Duration` 비교로 먼저 검사하므로 거대한 원본 날짜 차이를 `toNanos()`하여 overflow하지 않습니다. 시간창 안에서 합집합 길이는 3,600,000,000,000ns를 넘지 않고 active 수는 4,096 이하입니다.

## 알고리즘

| 구현 | 방법 | 시간 | 추가 메모리 |
|---|---|---|---|
| `QuadraticBoundaryScan` | 고유 endpoint 사이의 각 구간에서 모든 세션을 다시 검사 | O(n²) | O(n) |
| `SweepLineAnalysis` | TreeMap에서 같은 endpoint delta 집계 후 시간 순으로 한 번 순회 | O(n log n) | O(n) |

정렬한 endpoint가 최대 2n개이므로 기준 구현은 최대 O(n) 구간 × n개 세션을 검사합니다. 개선 구현은 최대 2n번의 TreeMap 갱신과 한 번의 순회로 같은 답을 구합니다. 이미 정렬된 입력을 가정하지 않으므로 O(n)이라고 표기하지 않습니다. 둘 다 입력을 수정하지 않습니다.

## 서로 독립적인 검증

1. **작은 격자 oracle**: true integer endpoint를 먼저 생성하고 64개의 tick 각각에 포함되는 세션을 직접 셉니다. timestamp 직렬화·offset·skew는 그 후에 부여합니다. oracle은 정규화/endpoint/sweep 코드를 호출하지 않습니다. 2,000개의 고정 seed 사례와 순서 변경을 확인합니다.
2. **Golden edges**: 인접, 중첩, 동시 시작/종료, 창 양끝 clipping, 창 밖 입력, 1ns, 같은 local clock의 서로 다른 offset, 양수·음수 오차, 날짜 경계, 잘못된 입력을 각각 고정합니다.
3. **큰 fixture 닫힌 형태 기대값**: sparse는 11ms 구간을 17ms 간격으로 배치하여 `covered=n×11ms`, `peak=1`입니다. nested는 모두 0에서 시작하고 종료를 1ms씩 늘려 `covered=n×1ms`, `peak=n`입니다. 최대 n=4,096의 두 구현을 이 기대값에 각각 대조합니다.
4. **UTC 오류 재현**: 09:00:00+09:00을 00:00:00Z로 해석해야 하지만 의도적 오류 구현은 offset을 버려 09:00:00Z로 취급합니다. 별도 테스트에서 올바른 10초/잘못된 0초 차이를 확인합니다. 그 오류 구현은 개선 알고리즘의 기준 구현이 아닙니다.

## 성능 측정의 범위

JMH는 알고리즘이 같은 immutable 정규화 입력으로 반환한 결과를 소비합니다. fixture별 expected 결과 검사는 fork의 trial setup에서 먼저 수행합니다. 문자열 파싱의 오류 수정과 알고리즘의 복잡도 개선을 서로 다른 증거로 제시하므로, 빠르지만 틀린 parser를 빠른 구현으로 비교하지 않습니다.

sparse/nested 두 분포는 endpoint 수와 겹침 정도가 다릅니다. 측정 결과는 이 고정 분포·크기·JDK·heap·GC·CPU 조건에만 해당합니다. fork별 표본과 allocation을 보존하며 평균의 비율을 tail latency나 운영 SLA로 표현하지 않습니다. 500ms warmup/measurement는 자원 예산을 둔 실험 설정이므로 JIT 안정성을 보장하지 않습니다. 결과 간 오차가 크면 반복 시간을 늘린 별도 새 실행으로 확인해야 합니다.
