# 센서별 결과 분포

[Java 처리 결과](https://devdooly.github.io/devdooly-platform-lab/#lab)에서 **센서별 결과** 탭을 선택합니다. 이미 읽은 실행의 전체 `outcomes`를 센서 ID별로 묶어 성공·실패·중복·대기를 비교하고, FAILED 사유를 펼쳐 볼 수 있습니다. 새 API 요청이나 서버 작업을 시작하지 않습니다.

## 사용 방법

1. 실행 ID·출처·원 관측 시각, 조회된 outcomes와 보고된 입력 건수를 확인합니다.
2. 센서 ID 포함 검색으로 센서 목록을 좁힙니다. 검색어의 앞뒤 공백을 제외하고 대소문자를 구분하지 않으며 eventId는 검색하지 않습니다.
3. 응답 첫 등장순, 실패 건수 많은순, 실패 비율 높은순으로 정렬합니다. 비율은 반올림 전 값으로 정렬하고 동률은 응답 첫 등장순을 유지합니다.
4. 처음 20개를 확인하고 **센서 20개 더 보기**로 늘리거나 **처음 20개로 접기**로 돌아갑니다. FAILED 사유는 센서별로 펼쳐 원문과 건수를 확인합니다.

검색·정렬 변경은 표시 개수를 20개로 되돌립니다. 다른 실행이나 출처로 전환하거나 같은 실행을 새로 조회해 응답이 바뀌면 센서 검색·정렬·표시 개수를 초기화합니다. 센서 목록의 검색·정렬은 이벤트 탭의 검색·상태·사유·선택·표 페이지와 공유 링크·CSV·JSON에 영향을 주지 않습니다. 아래 이벤트 이동 버튼은 별도로 조건을 바꿉니다.

결과 탭은 좌우 방향키로 순환하고 Home은 시계열, End는 센서별 결과로 이동합니다. 탭을 바꿔도 실행을 다시 조회하지 않습니다.

## 센서에서 이벤트로 이동

각 센서의 **이벤트 보기**는 해당 원문 sensorId가 정확히 같은 전체 이벤트를, **실패 이벤트 보기**는 그중 FAILED 행을 엽니다. 실패가 0건이면 실패 버튼을 표시하지 않습니다. `sensor-1`과 `sensor-10`, 대소문자·공백·빈 문자열을 구분하며 eventId의 같은 문자열은 일치로 세지 않습니다. 새 GET 없이 이미 읽은 outcomes만 좁힙니다.

이동하면 이벤트 탭으로 포커스를 옮기고 센서 조건과 전체/실패 상태를 적용합니다. 이전 검색어·사유·선택 이벤트를 지우고 표의 첫 페이지로 돌아갑니다. 그 뒤 검색·상태·사유 조건은 센서 조건과 함께 적용됩니다. **센서 조건 해제**는 정확 센서만 해제하고 나머지 조건을 유지하며, **검색·필터 초기화**는 센서까지 모두 지웁니다. 실행 변경·새로 조회에서는 다른 이벤트 조건과 같이 센서 조건을 유지하므로 같은 ID가 없으면 0건으로 남습니다. 센서 분포 자체는 계속 전체 outcomes를 집계합니다.

공유 링크에는 선택한 센서 원문을 `labSensor`로 보존합니다. 센서가 없는 기존 링크를 적용하면 정확 센서 조건을 해제합니다. 정확 센서가 있는 CSV·JSON은 조건을 포함한 형식2를 쓰며, 센서 조건이 없으면 기존 형식1을 유지합니다. [공유](event-share.md) · [저장 형식](event-export.md). 출처·원 관측 시각은 유지하며 다운로드·탭 이동으로 새 관측 시각을 만들지 않습니다.

## 집계의 범위

- **그룹:** 응답의 원문 sensorId가 정확히 같은 행을 묶습니다. 빈 문자열·공백·대소문자 차이는 서로 다른 센서 ID입니다. 화면은 JSON 문자열 표기로 이 차이를 구분합니다.
- **건수:** 동일한 eventId나 sequence가 있더라도 관측된 각 행을 집계합니다. 네 상태의 합은 센서별 조회 건수, 모든 센서의 합은 조회된 outcomes 건수입니다. 실행 요약의 successCount/failureCount로 개별 센서 결과를 채우지 않습니다.
- **비율:** `센서의 FAILED 행 수 / 센서의 관측 행 수 × 100`입니다. 소수점 아래 두 자리까지 표시합니다. 처리 시간·센서 장애율·실제 수율을 뜻하지 않습니다.
- **실패 사유:** FAILED 행만 원문 reason별로 집계합니다. 성공·중복·대기의 같은 사유 문자열은 FAILED 사유 수에 포함하지 않습니다.
- **관측:** 응답에 나타난 센서 수만 표시합니다. 보고된 입력과 조회 건수가 같아도 누락 부재나 전체 센서 수가 입증되지는 않습니다. 두 건수가 다르면 응답 행만 집계했다고 알립니다. 빈 결과를 누락 센서의 0건 결과로 채우지 않습니다.
- **출처:** live·게시 관측·고정 샘플을 구분하고 원래 observedAt/capturedAt을 유지합니다. 브라우저 조작으로 관측 시각을 새로 만들지 않습니다. PENDING 표시는 DTO 지원이며 실제 Java 경로가 대기를 생성했다는 증거가 아닙니다.

## 구현과 확인

2026-10-25 센서→이벤트 연결의 로컬 웹421개(실패·생략0), Astro78파일 진단0과4페이지 빌드를 통과했습니다. 실제1,000행 응답에서 max-sensor-099의 전체10·실패3·OUT_OF_RANGE1행(sequence996), 정확 조건만 해제한 FAILED/OUT_OF_RANGE100행과 파일 준비 안내 해제를 확인했습니다. JSON형식2의 원문 조건·원 관측 시각·sequence996과 CSV23열의context1/event1행을 실제 다운로드 파일에서 대조했습니다. 링크를 연 직후 미적용과 명시적 조회 후 같은 조건·1행 복원, 모바일375px 넘침0·17px·버튼50px 이상·Enter 이동 후 이벤트 탭 포커스, 부분검색AND·실행 변경/재조회 때 정확 조건 유지·없는 센서0행·전체 초기화도 확인했습니다.

빈·공백·대소문자·접두어 센서와 유효하지 않은 UTF-16, 실패·지연·잠금은 합성 모델/실제 handler·SSR 검사 범위이며 운영 입력에 주입하지 않았습니다. 최초 전체 검사에서는 기존 handler 테스트에 새 setter 의존성이 빠져 실패했고 테스트 harness를 보완한 뒤 통과했습니다. 별도 SSR 테스트의 속성 순서 가정 오류와 브라우저 다운로드 대기 시간 초과도 원 기록에 남겼습니다. 공개 게시·같은 main의 CI·Pages·실제 공개 결과는 변경 PR에서 로컬 확인과 구분합니다.

`lib/sensor-outcomes.ts`의 순수 집계·검색·정렬, `SensorOutcomeExplorer.tsx`의 별도 목록과 `LabExplorer.tsx`의 세 번째 탭으로 구성합니다. 모델의 독립 예상값, 실제 컴포넌트 렌더와 탭 키보드 핸들러를 검사하며 전체 웹·타입·빌드와 실제 로컬/공개 흐름 결과는 변경 PR에 기록합니다. 수행하지 않은 검증을 완료로 대신 표시하지 않습니다.

2026-10-24 로컬 웹373개(실패·생략0), Astro74파일 진단0과4페이지 빌드를 통과했습니다. 실제1,000행 응답의100개 센서에서 각10행=성공5·실패3·중복2·대기0, 실패비율30.00%와 FAILED 사유3종 각1건을 확인했습니다. 기존 이벤트 필터가 FAILED·OUT_OF_RANGE인 상태에서도 분포는 전체1,000행을 집계하고 공유 조건을 유지했습니다. 20→40개 더 보기, 정렬 후20개 복귀, 센서 검색·0건, 같은 실행 새 응답과 다른 실행 전환의 검색·정렬 초기화, 키보드 탭 순환과 모바일375px 가로 넘침0·17px·제어49px 이상을 확인했습니다. 다른12행 실행은 센서2개(8·4행), 각각25.00%를 표시했습니다. 이 결과는 해당 개인 합성 응답의 관측이며 센서 장애·성능 개선을 증명하지 않습니다.

첫 로컬 실시간 조회는 HTTP429로 게시 관측을 유지했습니다. 사용자가 누르는 것과 같은 명시적 실시간 조회로 API 연결을 복구한 뒤 위 실측 흐름을 확인했습니다. 자동 재시도나 운영 설정 변경은 추가하지 않았습니다. 빈/공백/특수 ID와 부분 관측은 모델·렌더 검사 범위이며 운영 데이터에 주입하지 않았습니다. 공개 결과는 같은 main의 게시 후 별도로 기록합니다.

Pages 토큰 교체·별도 K3s/Jenkins 기동 복원·예산 정책·PR #102와 운영 image/source pin은 유지합니다. 새 토큰·배포·자료 변경은 이 기능에 필요하지 않습니다.
