# 두 실행의 센서별 결과 비교

[두 실행 비교 화면](https://devdooly.github.io/devdooly-platform-lab/runs/compare/) · [전체 실행 비교](run-comparison.md) · [단일 실행 센서 분포](sensor-outcomes.md) · [현재 우선순위](../AUTONOMOUS_WORK.md#다음-작업의-우선순위)

전체 성공·실패 건수가 같아도 실패한 센서는 달라질 수 있습니다. 예를 들어 A에서 sensor-a가 실패하고 sensor-b가 성공한 뒤 B에서 반대 결과가 나오면, 전체 실패 차이는 0이지만 센서별 실패 차이는 각각 −1·+1입니다. 이번 개발 범위는 표시 중인 A·B 응답의 센서별 건수와 실패 비율을 나란히 보는 기능입니다. 기존 두 상세 GET의 결과를 사용하며 센서 탐색으로 새 API 요청이나 작업을 만들지 않습니다.

## 사용 순서

1. 기존 방법대로 A·B를 고르고 **두 실행 비교**를 눌러 두 응답을 읽습니다.
2. 센서별 비교에서 각 센서의 조회 건수·성공·실패·중복·대기와 실패 비율을 확인합니다. 차이 방향은 **B − A**입니다.
3. 센서 ID 포함 검색, **건수·관측 차이 있는 센서만**, 정렬을 조합해 목록을 좁힙니다. 검색은 앞뒤 공백과 대소문자를 무시하지만 센서 그룹의 원문 ID는 바꾸지 않습니다.
4. 응답 첫 등장순, 실패 건수 차이 큰순, 실패 비율 차이 큰순으로 정렬합니다. 차이 큰순은 부호를 제외한 크기를 사용하며 산정할 수 없는 차이는 뒤에 둡니다. 동률은 원래 순서를 유지합니다.
5. 처음 20개에서 **센서 20개 더 보기**로 늘리거나 **처음 20개로 접기**로 돌아갑니다. 관측된 쪽의 전체·실패 이벤트 링크로 상세에 이어갈 수 있습니다. 실패 0건인 쪽에는 실패 링크가 없습니다.

검색·차이 조건·정렬을 바꾸면 표시 개수를 20개로 되돌립니다. 새 비교의 두 응답을 모두 읽어 표시할 때 센서 검색·차이 조건·정렬·표시 개수를 초기화합니다. 위 A·B 선택만 바꾸었거나 조회 중·조회 실패인 동안에는 직전 정상 비교를 보존합니다. 센서 목록과 링크는 새 선택을 섞지 않고 그 표시 결과를 따릅니다.

## 건수와 미관측의 구분

- **센서 그룹:** 원문 sensorId가 정확히 같은 행을 묶습니다. 빈 문자열·공백·대소문자 차이를 구분하고 화면에는 JSON 문자열 표기를 사용합니다. A 응답의 센서 첫 등장순 뒤에 B에만 나타난 센서의 첫 등장순을 붙입니다.
- **다섯 건수:** 조회 행 수와 SUCCESS·FAILED·DUPLICATE·PENDING의 네 상태 건수입니다. 반복 eventId나 sequence도 각 관측 행으로 셉니다. 보고된 실행 총계로 센서별 수를 보충하지 않습니다.
- **실패 비율:** 각 센서의 `FAILED 행 수 / 관측 행 수 × 100`입니다. 실행 전체 입력 건수를 분모로 쓰는 기존 비교 비율과 다릅니다. 비율 차이는 퍼센트포인트(%p)이며 정렬에는 반올림 전 값을 사용합니다.
- **한쪽 미관측:** 한 응답에 센서가 없으면 **이 응답에 미관측**으로 표시합니다. 0건 센서를 만들거나 센서 추가·삭제로 단정하지 않습니다. 양쪽 모두 관측된 경우에만 건수·비율의 B − A를 계산합니다.
- **차이 조건:** 다섯 건수 중 하나라도 다르거나 한쪽만 미관측인 센서를 남깁니다. 실패 사유·값·이벤트 시각의 차이는 검사하지 않으므로, 이 조건에서 제외됐다고 모든 이벤트가 같은 것은 아닙니다.

각 응답의 조회 행 수와 보고된 입력 건수를 함께 확인합니다. 두 수가 같아도 전체 센서와 누락 부재를 증명하지 않습니다. 두 GET은 동일 시점의 원자적 관측이 아니며 출처·원 관측 시각·브라우저 수신 시각을 유지합니다. 결과의 원인, 같은 입력·코드 버전 여부, 실제 센서 장애나 수율 개선을 이 표로 증명하지 않습니다.

## 상세 이동·공유·저장 범위

센서의 전체·실패 이벤트 링크는 **표시 중인 비교**의 해당 실행과 원문 센서 정확 조건(`labSensor`)을 전달합니다. 미관측인 쪽에는 링크가 없습니다. 원문을 손실 없이 링크로 만들 수 없는 경우에도 링크를 만들지 않습니다. [기존 이벤트 공유 형식](event-share.md)을 사용합니다.

도착한 상세 화면에서 **공유한 실행·조건 조회**를 눌러 새 응답을 읽습니다. 비교 당시의 행·시각을 고정하지 않으므로 새 결과가 달라지거나 0건일 수 있습니다. 이 이동은 센서 목록 검색어가 아닌 원문 센서 ID의 정확 조건을 전달합니다.

기존 **비교 링크 복사**는 A·B 실행 ID만 담습니다. 센서 검색·차이 조건·정렬·표시 개수는 저장하지 않습니다. **비교 요약 CSV 다운로드**도 기존 실행 전체 요약·실패 사유 형식을 유지하며 센서별 행이나 센서 목록 조건을 추가하지 않습니다. 센서 상세의 이벤트 CSV·JSON은 별도 [이벤트 저장 형식](event-export.md)을 따릅니다. 이번 기능은 센서 비교 파일 내보내기나 오프라인 파일 비교를 제공하지 않습니다.

## 구현과 검증 상태

기존 `sensorOutcomeSummary`를 이용한 순수 비교 모델과 `SensorRunComparison` 화면을 기존 실행 비교에 연결합니다. 원 응답·행 순서·시각과 기존 비교 CSV·ID 공유 형식은 유지합니다.

2026-10-25 KST 로컬 웹439개(실패·생략0), Astro80파일 진단0과4페이지 빌드를 통과했습니다. 전체 검사 자체는 첫 실행에서 통과했지만 결과를 출력하는 로컬 실행기의 CP949 인코딩 오류가 뒤에 발생했습니다. 저장된 통과 로그를 확인하고 완료한 검사는 재실행하지 않은 채 출력만 고쳐 타입·빌드를 이어갔습니다. 별도 모델 검사의 첫 검색 기대값 오류1건도 제품 변경 없이 단언을 바로잡았으며 원 실패 로그를 남겼습니다.

실제 저장된12행(A)·1,000행(B)의 센서2/100개 합집합102개, 한쪽 미관측과 차이 미산정,20→40개 더 보기·정렬 시20개 복귀·공백/대문자 센서 검색과 차이 조건의1행·원시각 보존을 확인했습니다. A·B 선택만 바꿨을 때는 이전 비교·센서 검색을 유지하고, 새 비교 성공 후에는 센서 조건을 초기화했습니다. 같은 센서2개가 있는 두12행 실행은 각8/4행·실패비율25%와 다섯 차이0을 표시했고, 차이 조건으로0행을 확인했습니다. 모바일375px의 가로 넘침0·글자17px·검색 입력51.75px·이벤트 링크45.5px와 Space 키의 차이 조건 전환을 측정했습니다.

A의 sensor-b 실패 링크를 Enter로 열어 요청한 실행·원문 센서 조건을 확인했으나, 상세 화면 첫 API 조회와 명시적 실시간 조회1회는 HTTP429로 연결되지 않았습니다. 기존 게시 관측과 공유 적용 버튼 잠금을 보존했으며 이를 센서 이벤트 재조회 성공으로 기록하지 않습니다. 자동 재시도·조회 제한 변경·운영 배포는 추가하지 않았습니다. 같은 main의 CI·Pages와 실제 공개 비교·상세 이동 결과는 변경 PR 기록으로 별도 확인합니다.

전체 총계가 같은데 센서별 실패가 이동하는 반례, 빈/공백/대소문자/특수 ID·미관측·역순·비율 분모·절대 차이 정렬·원본 불변은 합성 모델·실제 컴포넌트 렌더와 독립 검토 범위입니다. 현재 운영 결과에 그런 입력을 주입하거나 같은 코드·입력·관측 시점의 동등성을 증명한 것은 아닙니다.

Pages 토큰 교체·별도 환경의 K3s/Jenkins 기동 복원·예산 정책·PR #102는 계속 보류합니다. 운영 API·worker·web image/source pin, 기존 서비스와 자료, 자동 이미지 제안 PR과 일시 중지한 세 자동화는 유지합니다. 새 토큰·별도 환경·운영 배포는 이 기능에 필요하지 않습니다.
