# 작업 관측 목록 검색·상태 필터

[작업·export 관측](https://devdooly.github.io/devdooly-platform-lab/#job-observation)은 작업마다 단계·원시 시각·파일 근거를 표시합니다. 길게 나열된 카드에서 특정 작업을 찾을 수 있도록, 이미 읽은 최대 20개 작업에 ID 검색과 두 상태 조건을 적용합니다.

## 사용하는 방법

1. **작업 ID 검색**에 ID의 일부를 입력합니다. 앞뒤 공백과 영문 대소문자를 구분하지 않습니다. 내부 공백과 기호는 입력한 문자 그대로 찾으며 정규식이나 여러 검색어로 해석하지 않습니다.
2. **작업 상태**와 **export 상태**를 고릅니다. ID·작업 상태·export 상태가 모두 맞는 작업만 표시합니다. 기본값은 모두 전체입니다.
3. **조회 목록 N개 중 조건 일치 M개**를 확인합니다. N은 현재 관측 응답의 목록 길이이며 전체 DB 작업 수가 아닙니다. 조건에 맞는 작업이 없으면 0건 안내와 조건 초기화를 제공합니다. 애초에 응답에 작업이 없는 경우의 안내는 별도로 유지합니다.
4. **조건 초기화**를 누르면 ID 검색을 비우고 두 상태를 전체로 돌립니다. 원래 응답 순서로 카드를 보여주며 작업 상태·건수·시각·파일 내용을 다시 계산하지 않습니다.

작업 상태와 export 상태는 별도 필드입니다. 예를 들어 명시적 종료인 TERMINATED/NOT_REQUESTED와 DB 완료 뒤 export 취소인 COMPLETED/CANCELLED를 구분합니다. 존재하지 않는 상태 조합으로 검색한 0건은 유효한 검색 결과이며 서비스 상태를 뜻하지 않습니다.

## 다시 조회할 때

자동·수동 조회로 관측이 갱신돼도 조건을 유지해 새 유효 목록에 적용합니다. 조회 실패·오래된 응답·같은 시각 내용 충돌 등으로 이전 유효 기록을 보존할 때도 조건을 유지합니다. 실시간 API에서 게시 기록으로 대체되는 경우도 같습니다. 새 목록에 검색한 ID가 없어지면 조건 일치 0건으로 표시하고 예전 카드를 섞지 않습니다.

API 대상 URL·관측 모드·실시간 우선 설정·게시 기록 URL이라는 조회 구성이 바뀌면 기존 관측 초기화와 함께 조건도 기본값으로 되돌립니다. 사용자가 조건을 초기화하는 동작은 조회 구성을 바꾸지 않습니다. 조회 중에는 검색·상태 선택·초기화만 잠그며, 화면 준비 전에는 관측 목록과 입력을 렌더하지 않습니다.

조건 변경은 추가 GET·서버 검색·작업 생성·재처리·export를 요청하지 않습니다. 기존 API 모드의 10초 조회와 8초 응답 제한은 유지합니다. 목록 조건은 상단의 runtime 마지막 DB 신호·슬롯·출처·관측 시각에 적용하지 않으며, 표시한 작업의 원문·파일 근거도 유지합니다. URL 공유·검색 결과 저장 기능은 이 작업 목록에 추가하지 않았습니다.

## 구현·검증 범위

`job-list.ts`는 검증된 JobObservation 목록에만 조건을 적용하고 원래 순서·작업 객체를 보존합니다. `JobObservationList.tsx`가 기존 작업 카드와 입력을 표시하며, 조건 상태와 조회 구성 변경 시 초기화는 부모 관측 카드가 관리합니다. DTO 검증·읽기·fallback·이전 관측 보존 계약은 바꾸지 않습니다.

합성 모델·렌더 검사는 여섯 가지 허용 상태 조합·검색과 상태 교집합·원본 0개와 조건 0개·입력 잠금·순서와 불변성을 다룹니다. 실제 공개 작업에 없는 상태를 운영에서 실행한 것처럼 보고하지 않습니다. 변경에 필요한 로컬·공개 확인 결과는 PR 기록에서 따로 연결합니다. 최대 20개 목록의 탐색 기능이며 성능 개선 수치를 측정하지 않았습니다.
