# 이벤트 표를 나눠 보기

[Java 처리 결과](https://devdooly.github.io/devdooly-platform-lab/#lab)의 **이벤트 상세 → 이벤트 상세 표**에서 검색 결과를 기본 25행, 선택에 따라 50·100행씩 봅니다. 표 위·아래에서 처음·이전·다음·마지막 페이지로 이동하며 현재 범위와 전체 페이지 수를 확인합니다.

## 표·검색·선택의 범위

페이지의 행 번호 범위는 검색 결과 안에서의 위치입니다. 응답의 sequence 값이 띄엄띄엄 있거나 eventId가 반복되어도 원래 순서를 유지하고 합치지 않습니다. 0건이면 ‘표시할 행이 없습니다’와 잠긴 이동 버튼을 표시합니다.

페이지를 이동해도 검색 조건과 흐름 선택은 유지합니다. 선택한 이벤트가 다른 페이지에 있으면 위치를 표시하고 **선택한 이벤트 행으로 이동** 버튼을 제공합니다. 흐름 목록에서 이벤트를 고르면 해당 행이 있는 페이지로 이동하고 기존 흐름 제목에 초점을 둡니다. 직접 페이지를 바꾸면 표 제목에 초점을 둡니다.

행 수를 바꿀 때 유효한 선택이 있으면 그 행이 있는 새 페이지로 이동하고, 선택이 없으면 첫 페이지로 돌아갑니다. 검색·상태·사유·초기화, 새 실행 조회나 새로고침으로 상세 자료가 바뀌면 첫 페이지에서 시작합니다. 공유 조회는 선택한 이벤트가 검색 결과에 있는 경우 해당 페이지를 엽니다. 공유·실행 조회 실패 시 이전 표시와 페이지를 유지합니다.

흐름 목록·선택 유효성·공유 링크는 전체 검색 결과를 사용합니다. [CSV·JSON 저장](event-export.md)도 페이지와 관계없이 조건에 맞는 전체 행을 담습니다. [공유 URL](event-share.md)에 페이지 상태를 추가하지 않으며 다시 적용할 때 선택 행의 위치를 찾습니다. 출처·상세 관측 시각과 원문 필드는 바꾸지 않습니다.

이미 읽은 응답의 표시 범위만 바꿉니다. 페이지 조작은 추가 GET·실행 생성·재판정·Kafka/S3 요청을 하지 않습니다. 긴 표의 탐색 편의를 위한 변경이며 성능 저하나 성능 향상 수치는 측정하지 않았습니다.

## 검증

로컬 웹 350개·생략 0, Astro 71파일 진단 0·4페이지 빌드를 통과했습니다. 0·25·26·1,000행 경계, 배열 위치와 sequence의 구분, 원문·행 참조·순서와 전체 검색 export 보존, 실제 핸들러의 페이지·조건·선택 전이를 검사합니다. 독립 모델은 계약 182사례·직접 207회 호출과 별도 비계약 특성 관찰 4건으로 구분합니다.

실제 로컬의 1,000건 실행에서 공유 sequence996의 976–1,000행·40페이지, 선택을 유지한 처음·다음 이동과 복귀, 50행의 20페이지와 100행의 10페이지, 상·하단 동기화·Enter 초점, 검색 0건과 새로고침·실행 변경의 초기화를 확인했습니다. 모바일 375px 가로 넘침 0·17px 글자·최소 45px 조작부를 확인했습니다. 정확한 head 검토와 병합 main의 CI·Pages·공개 결과는 PR에 별도로 남깁니다.
