# 입력 순서별 이벤트 응답 비교

[두 실행 비교](https://devdooly.github.io/devdooly-platform-lab/runs/compare/)에서 전체·센서별 집계 아래의 **입력 순서별 이벤트 응답 비교**를 사용합니다. 전체 실패 수와 센서별 분포가 같아도 어느 위치의 값·판정이 다른지 확인하는 기능입니다. 표시 중인 A·B의 기존 응답만 사용하며 새 실행이나 추가 GET을 요청하지 않습니다.

## 대응과 분류

두 응답에 나타난 `sequence`를 숫자 오름차순으로 나란히 봅니다. sequence는 관측된 입력 위치를 맞추는 기준이며 같은 실제 이벤트의 식별자가 아닙니다. eventId가 반복돼도 각각의 위치를 유지하고, 순서가 바뀐 행을 ID로 다시 짝짓지 않습니다.

| 분류 | 조건과 의미 |
| --- | --- |
| 대응 모호 | 한쪽이라도 같은 sequence가 복수 행이면 임의로 첫 행을 고르지 않습니다. 양쪽 후보 행과 건수를 보존하며 필드 차이를 계산하지 않습니다. 반대쪽이 미관측이어도 이 분류가 우선입니다. |
| 한쪽 미관측 | 한쪽 응답에 해당 sequence가 없습니다. 삭제·전체 입력 누락을 확정하거나 0값으로 채우지 않습니다. |
| 응답 입력필드 차이 | 양쪽 각각 1행이며 eventId·sensorId·eventTime·value 중 다른 필드가 있습니다. 판정 차이도 별도로 표시하지만 같은 입력에 대한 수정 효과로 해석하지 않습니다. |
| 판정 차이 · 응답 입력필드 일치 | 양쪽 각각 1행이고 위 네 보고 필드는 같지만 status 또는 reason이 다릅니다. |
| 관측 필드 일치 | 같은 위치의 네 입력필드와 두 판정필드가 같습니다. 전체 실행·원본 입력·실행 코드가 같다는 뜻은 아닙니다. |

문자열은 공백·대소문자·시각 표기를 바꾸지 않고 정확히 비교합니다. 숫자와 null은 구분하며 수치의 증감이나 시각의 정규화는 계산하지 않습니다. `value=null`은 원래 null·NaN·무한대가 같은 응답으로 나타난 것일 수 있어 원래 값을 복원할 수 없습니다. 앞선 이벤트 처리 문맥과 실행 당시 코드 버전도 이 DTO만으로 확인할 수 없습니다. 보고 필드가 같아도 원본 파일·바이트·전체 입력의 동일성이나 회귀·개선 효과를 증명하지 않습니다.

분류 건수는 이벤트 행 수가 아닌 **sequence 그룹 수**입니다. 양쪽 조회 행 수와 보고된 inputCount는 별도로 표시합니다. 분류 합계나 inputCount와 outcomes 길이의 일치만으로 응답의 완전성을 판단하지 않습니다.

## 목록 탐색과 이벤트 이동

ID 검색은 앞뒤 공백을 제외하고 대소문자 구분 없이 양쪽 모든 후보 행의 eventId·sensorId에서 부분 문자열을 찾습니다. 일치한 sequence 그룹의 후보 행은 잘라내지 않습니다. 분류 조건과 함께 적용하며 처음 20개부터 20개씩 더 볼 수 있습니다. 검색·분류를 바꾸면 처음 20개로 돌아갑니다.

초안 A·B 선택을 바꾸거나 조회가 실패하면 기존에 표시된 응답과 목록 조건을 유지합니다. 새 A·B 조회가 모두 성공해 표시 응답이 교체될 때 검색·분류·표시 수를 초기화합니다. 준비 전·조회 중에는 조작을 잠그며 응답 출처와 원 관측·수신 시각은 유지합니다.

해당 side에서 sequence가 유일한 행에만 **이벤트 보기** 링크를 제공합니다. 반대쪽이 모호하더라도 유일한 쪽의 이동은 가능합니다. 링크는 실행 ID와 sequence를 전달하며 도착 화면에서 명시적으로 다시 조회해야 합니다. 비교 당시 응답·시각을 고정하지 않고 새 조회에서 같은 행이 유지됨을 보장하지 않습니다. 중복 sequence 쪽은 임의 행으로 연결하지 않습니다.

기존 비교 CSV는 실행 전체 요약이며 이 이벤트별 표와 검색·분류 조건을 담지 않습니다. 기존 A·B ID 공유 링크에도 이 목록 조건을 추가하지 않습니다. 기존 이벤트 내보내기·공유 형식과 Java/API·운영 image/source pin은 유지합니다.

## 검증 범위

모델13개·SSR8개는 최초 실행에 통과했습니다. 전체 웹 최초460개 중459개 통과·1개 실패는 기존 Kafka loopback HTTP 검사의 headersReceived 기대값과 관측이 달랐던 경우입니다. 새21개는 모두 통과했고 Kafka 파일 단독23개와 파일 직렬 전체460개는 통과했습니다. 최초 실패·단독·직렬 로그를 각각 보존하며 원인은 미확정입니다. 관련 Kafka 코드·테스트는 수정하지 않았습니다. Astro82파일 진단0·4페이지 빌드를 확인했습니다.

로컬 실제 GET에서 A12행·B1,000행의 sequence1,000그룹을 비교해 입력 필드 차이12·한쪽 미관측988을 확인했습니다. 20→40개 표시와 분류 변경 시20복귀, 공백·대문자 센서 검색10개 및 검색 전후 원 시각 보존을 확인했습니다. 초안 선택만 바꾸면 이전 응답·조건을 유지했고, 새 A12·B12행 조회 성공 후에는 조건을 초기화하고 비교 필드 일치12개를 표시했습니다. 판정 차이 분류0개와 evt-006 검색의 sequence7·양쪽 FAILED/OUT_OF_RANGE·value120도 확인했습니다. 이 두 실제 실행에서 순수 판정 차이를 관측한 것은 아닙니다.

조회 실패 보존은 미존재 ID의 HTTP404에서 이전 pair·검색 조건·출처가 유지됨을 확인한 범위입니다. 실제 조회가 빠르게 완료돼 busy 순간을 브라우저에서 포착하지 못했으므로 입력·링크 잠금은 SSR 검사로 구분합니다. 모바일375px에서 가로 넘침0·본문17px·검색55.75px·상세 링크45.5px와 Enter로 입력 필드 접기를 확인했습니다. 개별 상세 링크는 실제 href의 실행 ID·중립 조건·sequence7을 확인했으며 도착 화면의 재조회는 공개 검증 단계에서 별도로 기록합니다.

로컬 최초 직접 연결은 원인 미확정 NETWORK 오류, 개발 프록시는 sandbox 네트워크 EACCES에 따른 HTTP502를 반환했습니다. 허용된 네트워크의 localhost 개발 서버에서 기존 공개 GET을 읽어 위 결과를 확인했으며 운영 라우트·인증·API 설정은 바꾸지 않았습니다. 이 준비 오류를 제품 수정이나 운영 복구로 표시하지 않습니다.

합성 DTO의 판정 차이·중복 sequence·원문 경계와 실제 공개 응답은 구분하며 운영 입력·실패 주입은 하지 않았습니다. 정확한 source 검토·main CI·Pages·실제 공개 확인은 해당 변경 PR에 별도 결과로 기록합니다. 로컬 결과를 공개 완료나 장기 가용성으로 간주하지 않습니다.

Pages 토큰 교체·별도 환경의 K3s/Jenkins 기동 복원·자원 예산 정책·PR #102는 보류합니다. 기존 서비스·데이터와 자동 이미지 제안 PR·다른 PAUSED 자동화는 변경하지 않습니다.
