# 요청한 실행과 상세 응답의 ID 일치

상태: **2026-10-21 UTC 로컬 RED/GREEN 검증 완료 · 공개 반영 전**. 실행 결과 선택 표시를 개선한 뒤, 요청 ID와 다른 상세 응답도 형식만 정상이면 표시될 수 있는 검증 공백을 확인했습니다. 실제 운영에서 잘못된 응답이 발생했다는 기록은 아닙니다.

## 수정 범위

[fetchRun](../../../apps/lab-web/src/lib/api.ts)의 기존 상세 형식 검사에 `detail.id !== id` 거부 조건 한 줄을 추가했습니다. 서버의 상세 조회는 요청 ID로 실행과 outcome을 찾고 같은 실행 ID를 반환하며, 다른 ID로 바꾸는 별칭 계약은 없습니다.

URL·GET·redirect·credentials·공개 API 설정과 기존 고정 오류 문구는 유지합니다. 정상 상세 조회와, 선호 ID가 목록에 없으면 첫 실행을 선택하는 동작도 유지합니다. 목록과 상세를 따로 조회한 시각·수치까지 모두 같게 강제하는 변경은 아닙니다.

## 먼저 실패를 확인한 회귀

기존 production에 [API 테스트](../../../apps/lab-web/tests/api.test.ts)와 [관측 fallback 테스트](../../../apps/lab-web/tests/observation.test.ts)만 먼저 붙였습니다. loopback HTTP 서버가 형식상 유효하며 목록에도 있는 다른 실행의 상세를 반환하도록 구성했습니다.

- 직접 상세 조회와 목록을 통한 상세 조회가 모두 거부돼야 하는데, 기존 코드는 둘 다 `fulfilled`로 반환했습니다.
- 잘못된 live 상세를 받으면 정상 게시 기록을 선택해야 하는데, 기존 코드는 `live`를 선택했습니다.
- Node의 집중 검사16개는 통과13·실패3·생략0, 종료값1이었습니다. 실패3에는 하위 검사 실패를 집계한 부모 그룹1개가 포함되므로 서로 다른 결함3개로 세지 않습니다.

이후 production 한 줄을 적용한 전체 웹 검사는209개 통과·실패0·생략0, 종료값0이었습니다. Astro 타입 검사47파일의 오류·경고·힌트0와 프로젝트 경로의 정적2페이지 빌드도 확인했습니다.

정상 ID·선호 ID 부재 시 첫 실행 선택, 목록에 포함된 다른 ID의 상세 거부, 정상 게시 기록으로의 fallback과 캐시 보존을 확인합니다. 두 잘못된 API 호출의 정확한 GET5개와 거부 결과, fallback 경로의 정확한 GET5개 및 전체 기록 동등성을 검사합니다. 구현 함수를 mock으로 바꾸지 않았고 새 의존성을 추가하지 않았습니다.
